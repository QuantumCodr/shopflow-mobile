# ShopFlow project status

**Documentation review date:** 30 October 2026  
**Repository reviewed:** `QuantumCodr/shopflow-mobile`, default branch `main`

This page separates code that is present from integrations and behaviours that still need verification. A screen existing in Flutter does not, by itself, prove that the full workflow is production-ready. The local authentication code shared during the development conversation is ahead of the GitHub `main` branch snapshot inspected on this date; reconcile and push those local changes before treating the branch as the canonical implementation.

## 2. Database integration blockers

The current Flutter repositories call these PostgreSQL functions:

| Function | Called from | Present in `SHOPFLOW_DATABASE.sql`? |
|---|---|---|
| `receive_stock` | `InventoryRepository.receiveStock` | Yes |
| `adjust_stock` | `InventoryRepository.adjustStock` | No |
| `complete_sale` | `PosRepository.completeSale` | No |

The canonical bootstrap comments also state that checkout still needs a single tested transaction. Until the missing functions are implemented, reviewed, deployed and tested, a fresh Supabase project created only from this file is not sufficient for the complete inventory-adjustment and POS workflows.

Do not work around this by granting direct client writes to `inventory`, `stock_movements`, `sales` or `sale_items`. The database should enforce authorization and commit related changes atomically.

## 3. Client/database contract mismatches

### Product units

`ProductService.units` accepts `dozen`, but the checked-in SQL unit constraint allows `bag` and does not allow `dozen`. Align these lists before relying on all visible unit choices.

### Quantity precision

Inventory services and PostgreSQL support quantities with up to three decimal places. POS models and repository use integer quantities and reject fractional stock. Fractional selling is not supported by the current POS.

### Database bootstrap files

The root contains both `SHOPFLOW_DATABASE.sql` and `shopflow_supabase_fresh_install.sql`. They are both bootstrap-style SQL files. Keep one clearly maintained canonical source and compare their contents before running either. Do not execute both sequentially against the same database.

## 4. Offline support

`sqflite` is listed in `pubspec.yaml`, but the inspected `lib/` source does not include a completed SQLite repository/cache layer, an offline write queue or transaction synchronization. The current verified operating model is online Supabase access. Offline reading and offline sales should be considered unimplemented until demonstrated by code and tests.

## 5. Testing

The checked-in `test/widget_test.dart` is currently empty. A successful `dart analyze` is useful static-analysis evidence, but there is not yet a substantial automated test suite visible in the repository. Priority test areas include:

- Money parsing and formatting.
- Product/category validation and model parsing.
- Inventory quantity validation and stock movement rules.
- POS cart calculations and receipt parsing.
- Shop ownership and RLS behaviour.
- Atomic stock receiving, stock adjustments and checkout.
- Authentication callback handling on Chrome and Android.

## 6. Authentication email delivery

Password recovery is present in the application code but has not yet been confirmed end to end. The current development project has encountered authentication email sending limits. Configure a suitable custom SMTP provider for regular testing and future user delivery, then retest the complete reset flow on each supported platform.

For browser PKCE testing, use the same browser profile and exact origin (scheme, hostname and port) for the reset request and callback. Do not reuse expired or previously exchanged recovery links.

## 7. Licensing

No `LICENSE` file is present in the inspected repository tree. Choose and add a license before describing the repository as officially open source. A public GitHub repository without a license does not automatically grant reuse rights.

## 8. Recommended next work

1. Reconcile the deployed Supabase schema with `SHOPFLOW_DATABASE.sql` and keep one canonical bootstrap/migration history.
2. Implement and test `adjust_stock` as an atomic, authorized stock update plus movement record.
3. Implement and test `complete_sale` as an atomic, authorized checkout that locks/checks stock, calculates authoritative prices and totals, writes sale and sale items, deducts stock and records negative sale movements.
4. Align product units between Dart validation and PostgreSQL.
5. Verify password recovery with custom SMTP on Chrome and Android.
6. Add focused automated tests for money, validation, models, POS calculations and database transactions.
7. Decide whether offline caching is a real V1 requirement. If yes, design it explicitly rather than relying on the unused package dependency.
8. Select and add a project license if open-source distribution is intended.

## 9. Release-readiness rule

Do not mark a workflow production-ready solely because its screen is visible or static analysis passes. A workflow is ready only after its UI, service, repository, deployed database contract, authorization rules, failure handling and relevant tests have all been verified together.
